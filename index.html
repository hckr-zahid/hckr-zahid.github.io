CyberGun — Static & Dynamic Threat Detection System

Modular malware-detection framework combining static signatures with ML-driven behavioral detection

Python 3 PyQt5 LightGBM YARA SQLite EMBER Dataset
Source Code Download Thesis

Architecture & Modules

Designed a multi-engine detection pipeline coordinated by a central DynamicEngine. Four modular sensors run concurrently:

  • Behavioral Engine — process execution tree analysis
  • System Activity Engine — disk I/O and CPU spike monitoring
  • USB Monitor — peripheral insertion event tracking
  • Sandbox Simulation Engine — controlled dynamic execution

Detection Layer

Static detection combines:

  • 3,160,113-entry SQLite threat hash index for rapid file matching
  • Custom YARA heuristics and byte-signature pattern matching
  • LightGBM classifier trained on EMBER and CIC benchmark datasets for PDF and PE structural anomalies (pdf_model.lgbm)

Interface & Containment

Asynchronous PyQt5 dashboard with a custom SignalBus pattern provides tabbed views: Dashboard, System Status, Threat Logs, Behavior Feed, Network Feed, and Quarantine. Detected threats are moved to an encrypted Quarantine Zone with SHA-256 hashes, original paths, and timestamped audit logs.

Security Research

PowerShell Static Code Analysis

Static Analysis Only · No Dynamic Execution

MAS AIO — PowerShell Activation Workflow Static Security Review

GitHub Repo Read Report (PDF)
Scope & Methodology: This research is based entirely on static source-code analysis using Abstract Syntax Tree (AST) inspection and manual code review. The analyzed scripts were not executed as part of this research. Findings describe observed code behavior and potential risks identified through static analysis alone. This is not a dynamic malware analysis report.

Research Question

What system-level operations, persistence mechanisms, and security risks can be identified through static analysis of the PowerShell-initiated workflow at irm https://get.activated.win | iex and the associated MAS_AIO.cmd script?

Method

Abstract Syntax Tree (AST) parsing and manual review of 10,000+ lines of PowerShell and batch script. No code was executed. Findings are limited to observable code structure, string literals, and control flow.

Key Dimensions Examined

  • Licensing Hooks: HWID ticket generation, KMS38 registry manipulation, Ohook DLL replacement
  • DLL Replacement: Targeted substitution of Windows licensing libraries (sppc.dll)
  • Scheduled Task Persistence: Task Scheduler renewal routines and execution hooks
  • Registry & Service Changes: Software Protection Platform service state modifications
  • Remote Download Vector: Security implications of the pipe-to-shell pattern without cryptographic validation

LAB 01

AD DS & VMware Enterprise Lab — 6 Implementation Phases

Phase 01

Isolated Virtual Switching

Configured custom host-only switch (VMnet10) bound to 10.1.1.0/24, isolating the testbed from physical networks.

Phase 02

Static IP & Network Diagnostics

Provisioned DC01, resolved ARP address collision on 10.1.1.1, and statically bound 10.1.1.10/24 with loopback DNS resolver (127.0.0.1).

Phase 03

AD DS Forest Root Promotion

Promoted DC01 to forest root domain controller for zroots.local (Windows Server 2016 functional level) with Global Catalog, authoritative DNS, and DSRM password protection.

Phase 04

OU Hierarchy & Tiered RBAC

Structured OU taxonomy separating computers, servers, and users. Engineered security groups: Administrators, IT-HelpDesk, Staff, Students, Management — enforcing least privilege.

Phase 05

NTFS Hardening & SMB Shares

Created C:\CompanyData share structure, severed inherited ACEs, established explicit Modify/Read ACLs per department, and restricted SMB share permissions.

Phase 06

Domain Join & Kerberos Validation

Joined WIN10-01 to zroots.local, verified DC locator via nltest /dsgetdc, and confirmed effective Kerberos token group SIDs via whoami /groups.

LAB 02

Group Policy Management & Verification

A

GPO Creation

New GPO created in GPMC and placed in the Group Policy Objects container. At this stage, the GPO exists but is not linked to any OU and has not applied to any machine.

B

GPO Linking

GPO linked to the target Organizational Unit. Linking establishes scope; settings are applied when the client refreshes Group Policy (at logon or via gpupdate /force).

C

Verification on WIN10-01

gpupdate /force triggered on the domain-joined client. Policy application confirmed via gpresult /r (elevated). Running without elevation returns Access Denied for computer-scope results — this is expected Windows behavior, not a configuration error.
